# 穿梭 · 同步中转（dsh-sync-shuttle）

两台电脑**不同时开机**也能同步文件的 DSH 插件。

原理：把目录打包成 **ZIP**、自行切成固定大小的分片，写入一个**远端存储后端**；
另一台电脑从同一后端读回分片、逐片校验、拼回整包、解包，**镜像覆盖**本地目录。

远端只作中转站，不需要任何一台机器常开，也不需要自建服务器。

当前支持一种存储后端：**QQ 邮箱（IMAP）** —— 详见 [存储适配器](#存储适配器) 一章。
邮箱后端下，一台机器把数据写进自己邮箱的私人文件夹，另一台登录同一账号读回。

归档是**内置纯 JS 实现**（`@zip.js/zip.js`），**不需要在机器上安装 7-Zip 或任何外部命令**。

---

## 快速开始

1. 在邮箱网页版开启 **IMAP** 服务并生成**授权码**
   （QQ 邮箱：设置 → 账号 → POP3/IMAP/SMTP 服务 → 开启 IMAP → 生成授权码；
   授权码只显示一次，**不是登录密码**）
2. 打开左侧栏 **穿梭 · 同步中转** → 设置 → 填邮箱地址 + 授权码 → 保存 → 测试连接
3. 项目页 → 新建项目（项目名 + 本地目录）→ 上传
4. 另一台电脑：同样配置邮箱（同一个账号）→ 刷新项目页 → 给项目绑定本地目录 → 下载并镜像

## 概念

| 概念 | 说明 |
|---|---|
| **项目** | 一个名字 + 一个本地目录。名字区分大小写与全半角，创建后不建议改名。 |
| **版本** | 每次上传生成一个版本（时间戳 `Version` + 随机 `Version-Id`）。默认只保留最新一版。 |
| **镜像** | 下载后目标目录与源机该目录**完全一致**：缺的补上、多的删掉、内容不同的覆盖。 |
| **保留上一版** | 单项目可选：保留最近 2 个版本，旧版可随时下载回滚。 |
| **分片** | 归档按适配器声明的 `volumeBytes` 切片；切片是插件自己做的，不是归档库的能力。拼回去就是标准 `.zip`。 |
| **存储后端** | 负责「把分片存到哪儿」的实现（当前为 `qqmail`）。见 [存储适配器](#存储适配器)。 |

> **关于加密**：本版**不支持**加密。ZIP 的 AES 只加密文件内容，文件名永远明文存在中央目录里，
> 无法隐藏「你同步了哪些文件」。因此**不要把敏感数据用本插件同步到不可信邮箱**。

项目卡片三种外观：

- **蓝实心「已联动」** —— 远端有版本、本机有目录绑定
- **灰虚线「待绑定」** —— 远端有版本（另一台传的），本机还没指定目录
- **蓝虚线「未上传」** —— 本机建了项目，还没传过

## 数据完整性

**每一次数据交接都算哈希，下一跳必须重算并比对；不一致就停在那里，绝不静默继续。**

```
① 源目录 ──打包──▶ ② 归档 ──切片──▶ ③ 分片 ──写入──▶ ④ 远端存储
                    校验A            校验B            校验C(回读)
                                                            │
⑦ 目标目录 ◀──解包── ⑥ 归档 ◀──拼回── ⑤ 下载的分片 ◀────────┘
   校验F                        校验E        校验D
```

- **校验 A**：打包后立刻逐条目重算 **CRC32** 比对中央目录声明值（zip.js 的 `getData()` 本身**不校验 CRC**，
  实测把数据区改坏一个字节它照样返回全量数据，所以这一步必须自己算）
- **校验 B**：逐片 SHA-256 + 片数 = `ceil(归档字节 / 分片大小)`
- **校验 C（回读）**：写入后**重新列一次、逐片读回、重算 SHA-256 比对**。
  这一步是整套设计的核心 —— **"写入成功"绝不等于"能读回来"**。此步默认强制、不提供跳过开关。
- **校验 D**：逐片下载后立即比对 SHA-256，不符就重下该片
- **校验 E**：拼回后整包 SHA-256 必须等于清单里声明的 `Archive-Sha256`
- **校验 F**：解包后比对文件数与总字节

三道护栏：

1. **新版本校验通过前，旧版本一封不删** —— 远端任何时刻至少有一个完整可用版本
2. **哈希值跟着数据走** —— 体积与哈希随分片一起存，不依赖后端的 size 字段
3. **元数据随每个分片冗余一份** —— 12 片就是 12 份清单，删到只剩 1 片仍知道应该有哪几片

> 诚实边界：这套保证「损坏能被发现」，不保证「数据永不丢」。
> 只留最新版时，若新版被外部删除则无备份可回；存储容量满会被服务商清理；
> 打包过程中源目录被改动，CRC 校验发现不了语义不一致。

## 并发控制：远端锁

两台电脑同时操作会互相删分片、下载到半套数据。插件用**锁的原子创建**做全局互斥。

```
锁（一个专用对象）← 创建成功 = 抢到锁；已存在 = 判负。判定由服务器仲裁，无竞态
   └ 锁信息：owner / nonce / at / ttl / op
```

- **租期 300 秒，心跳 60 秒续期** —— 进程崩溃、断网、强杀都不会留下永久死锁
- **释放前必须确认 nonce 还是自己的**，否则会误删别人正在生效的锁
- **陈锁判定必须用服务器时间**，不能用本地时钟（两台机器时钟可能差几分钟）
- **浏览清单不持锁** —— 否则一台机器上传大包时，另一台连页面都打不开
- **拿不到锁默认自动排队**（3 秒 × 20 次），绝不静默失败；顶栏显示对方在做什么

锁的**原语**由适配器实现（它才知道怎么原子创建），**重试 / 心跳 / 陈锁判定**在通用层 `lib/lease.js`。
各后端的原子性来源见 [存储适配器](#存储适配器)。

## 存储适配器

核心流程（打包 / 上传 / 回读校验 / 清单 / 下载 / 镜像 / 锁）**不认识具体后端**，
只依赖 `lib/storage/adapter.js` 定义的契约。

```
核心流程  upload / download / manifest / config-store
   │      只认 adapter 契约
   ▼
租约层    lib/lease.js（重试、排队、心跳、陈锁判定、nonce 校验）
   │      只认 lock* 四个原语
   ▼
适配层    lib/storage/qqmail.js
   ▼
传输层    lib/mail.js / envelope.js / builder.js（IMAP 内部实现）
```

### 接口约定

```js
{
  id, displayName,
  volumeBytes,        // 分片大小：适配器的固定常量，不可由用户配置
  maxObjectBytes,     // 单对象硬上限；null = 不限制

  open() / close() / ping()

  put({ collection, key, meta, body })  // => { accepted: true }
  get({ collection, ref })              // => { key, meta, body }
  list({ collection })                  // => [{ ref, key, meta, sizeBytes, createdAtMs }]
  remove({ collection, refs })          // => { removed }

  lockTryCreate({ owner, nonce, ttlMs, op })  // => { acquired, holder? }
  lockInspect()                               // => { holder, serverTimeMs } | null
  lockRenew({ nonce })                        // => { ok }
  lockRelease({ nonce, force })               // => { released, reason }

  capacity()   // => { totalBytes, exact, note }
}
```

`collection` 只有两个值：`data`（项目分片）、`config`（本机配置备份）。

### 三条硬性要求（实现新后端时必须遵守）

1. **`meta` 必须随每个对象走**，不能每个版本只写一份清单。
   这是「护栏 3」的实现要求：删到只剩 1 个对象仍要知道该有几个。
   SMB 这类没有邮件头的后端，必须给每个分片旁挂 `<分片>.meta.json`。

2. **`lockInspect()` 必须回传 `serverTimeMs`**。
   陈锁判定用服务器时间，不用本地时钟。
   拿不到服务器时间时**不许判陈**，按活跃处理——宁可排队，也不能误抢别人正在生效的锁。

3. **`list()` 必须给出 `createdAtMs`**（服务器记录的创建时刻）。
   「哪个版本最新」由它决定，否则两台机器可能算出不同结果。

另有一条：**`put()` 不返回 ref，也不承诺「写完立刻读得到」**。
写入成功 ≠ 读得回来；定位由调用方在所有写完之后 `list()` 一次解决。

### 已实现：qqmail（QQ 邮箱 / IMAP）

> 名字叫 `qqmail` 而不是 `imap`，因为实现依赖的是**腾讯 QQ 邮箱的实测行为**，
> 不是 IMAP 协议通用要求。网易 163 / 126 / yeah 走同一套协议栈共用本实现，但**未真机实测**。

| 项 | 值 / 实现 |
|---|---|
| `volumeBytes` | **40 MiB**（QQ 单封附件上限 ≈51 MiB，留 11 MiB 余量） |
| `maxObjectBytes` | **51 MiB**（实测值，52 MiB 起报 `TOOBIG`） |
| `collection: 'data'` | 邮箱文件夹 `Sync-Shuttle` |
| `collection: 'config'` | 邮箱文件夹 `Sync-Shuttle-Config` |
| 锁 | 邮箱文件夹 `Sync-Shuttle-Lock` 的**原子 CREATE**（服务器返回 `ALREADYEXISTS` 判负） |
| `ref` | 邮件 **seq**（会话内有效，不跨会话缓存） |
| `meta` 载体 | 邮件自定义头 + 正文完整清单（双份冗余） |
| `createdAtMs` | 邮件 **INTERNALDATE**（服务器时钟，误差 < 1 s） |
| `capacity()` | 手填基线，`exact: false`（QQ 不提供 QUOTA） |

**只走 IMAP `APPEND`，不走 SMTP**：一封信只存一份、不产生"已发送"副本、
不触发新邮件提醒、不进收件箱、不消耗发信额度。

#### IMAP 实测约束（换服务商需重测）

| 坑 | 表现 | 应对 |
|---|---|---|
| **UID 不可靠** | `fetchOne(uid, {uid:true})` 一律返回空 | 全部用 **seq** 读；seq 会漂移，不跨会话缓存 |
| **`RFC822.SIZE` 谎报** | 13.5 MiB 报 887 字节 | 不用 `client.download()`；体积/哈希自带在邮件头 |
| **EXISTS 不刷新** | append 后同连接 `fetch('1:*')` 仍返回 0 封 | 读完 `mailboxClose()` 再重新 SELECT |
| **单封上限** | 附件 ≈51 MiB（raw 68.9 MiB），52 MiB 起 `TOOBIG` | 分片固定 40 MiB |
| **QUOTA 不可用** | `getQuota()` 返回 false | 容量靠手填 + 自算（Σ Volume-Bytes，**小于**真实值） |
| **自定义头会编码** | 中文头值被 RFC 2047 编码，mailparser 也不解码 | 头值**必须纯 ASCII**，项目名走 `encodeURIComponent` |
| **头名被规范化大小写** | `X-SS-Lock-Owner` → `X-Ss-Lock-Owner` | 读头必须 `toLowerCase()` |
| **DELETE 非空文件夹失败** | `Error: Command failed` | 先清空邮件再删文件夹 |
| **mailbox lock 不可重入** | 持锁时再取锁 → 永久死锁 | 每次取锁独立作用域，出来立刻 release |

实测吞吐：写入 **8–27 MiB/s**，读回 **≈3.8 MiB/s**。

#### QQ 的容量口径

`QUOTA` 不可用，所以容量条显示的是「**本插件占用** vs 你手填的邮箱总容量」，
不包含收件箱、已发送等其他文件夹，所以**必然小于**邮箱真实用量。设置页有 ⓘ 提示。

### 未实现：局域网 SMB

设计上已预留，接进来只需：

1. 写 `lib/storage/smb.js` 实现上面 13 个方法
2. 在 `lib/storage/index.js` 的 `STORAGE_KINDS` 登记
3. 工厂加一个 `case 'smb'`

`upload` / `download` / `manifest` / `config-store` / `lease` **一行都不用改**。

实现时要注意的差异：

| 维度 | qqmail | SMB |
|---|---|---|
| 分片上限 | 51 MiB 硬限 | 几乎无限，`maxObjectBytes` 可设 `null` |
| 合理的 `volumeBytes` | 40 MiB | 可设大得多，或干脆不分片 |
| `meta` 载体 | 邮件头 + 正文 | 没有头，需旁挂 `<分片>.meta.json` |
| 锁的原子性 | 文件夹 CREATE | 目录 `mkdir`（同样是服务器仲裁） |
| `serverTimeMs` | 邮件 INTERNALDATE | 锁文件 mtime |
| `createdAtMs` | 邮件 INTERNALDATE | 文件 mtime |
| `capacity()` | 手填，`exact: false` | `statfs` 真实值，`exact: true` |

> 注意：SMB 需要有一台机器或 NAS 常开，不具备 IMAP 那样「两台不同时开机也能同步」的能力。

## 配置

见 `cordis.patch.yml`。主要项：

| 键 | 默认 | 说明 |
|---|---|---|
| `storageKind` | `qqmail` | 存储后端（目前只有 qqmail） |
| `folderPrefix` | `''` | 远端文件夹前缀。**生产保持为空**；测试用它把数据隔离到独立文件夹 |
| `preset` | `qq` | 邮箱服务商预设：`qq` / `163` / `126` / `yeah` / `custom` |
| `volumeGapMs` | `600` | 片间间隔，避免触发服务商限流 |
| `keepPrevDefault` | `false` | 新项目是否默认「保留上一版」 |
| `capacityBytes` | `12884901888`（12 GiB） | 容量基线，**手填**（QQ 无 QUOTA 接口）。见下方说明 |
| `lockTtlMs` | `300000` | 租期 5 分钟 |
| `lockHeartbeatMs` | `60000` | 心跳 60 秒 |
| `readOnly` | `false` | 只读模式：只浏览与下载，禁止远端写操作 |

`preset` / `capacityBytes` 等是 **qqmail 专用**的，其他后端会忽略不适用项。

### 为什么容量基线是 12 GiB 而不是 16 GiB

QQ 免费邮箱上限是 16 GB，但这里**刻意只用 12 GB**，留约 4 GB 余量给：

- 收件箱、已发送、其他文件夹（本插件无法统计，也不该去统计）
- 服务商自身的对齐损耗（附件编码、索引等）
- 临时峰值

**邮箱被占满会导致连正常收信都被拒**——风险远大于少存几 GB。
而且容量统计口径（Σ Volume-Bytes）本身**小于**真实占用（见下方「QQ 的容量口径」），
再贴着实测上限用，等于把两处误差叠在一起。

达到 12 GiB 时上传会被拒绝，提示「请先删除旧项目或调整容量设置」。
确实需要更多空间时，可以在 `cordis.patch.yml` 里调高 `capacityBytes`——
但请自己算好留多少，别把它设成邮箱上限。

## 安装

从 GitHub 安装。仓库为 public，目标机器不需要配 SSH key 或凭据助手。

在 DSH 里让 agent 执行：

```
plugin_manager  action=install_bundle
                target=github:你的用户名/sync-shuttle#<40 位完整 commit>
```

或者直接在 Web 侧的插件页安装。

### 前置要求

| 项 | 说明 |
|---|---|
| `git` | 目标机器需要装有 git（安装器会用它拉取仓库） |
| `pnpm` | 没装也没关系，DSH 自带的会被优先使用 |
| 网络 | 首次安装会 `npm install` 依赖（含 `@zip.js/zip.js`） |

### 必须知道的机制

| 事项 | 行为 |
|---|---|
| 安装前预检 | GitHub 仓库会先跑 `git ls-remote` 探测，超时 5 秒（`githubConnectionTimeoutMs`）。探不通就在 pnpm 启动前中止，报 `failedAt: 'spec-host'` |
| **必须 pin 完整 commit** | 只有 pin 到 **40 位完整 commit** 的 git 规格才能用 `updateBundle` 更新。写分支名、标签、范围一律**不可更新**，因为失败重装回不去 |
| 更新 | 推新 commit → `updateBundle` 传新的 40 位 commit。新旧必须 pin 同一仓库同一 `path:` |
| 已装过再装 | HMR 下返回 `already-installed`；换版本要先移除再安装 |
| **换代码要重启** | 替换正在运行的包，必须重启 DSH 才会加载新的模块代 |

取当前 commit 的完整哈希：

```powershell
git rev-parse HEAD
```

### 装完先做三件事

1. **确认 `folderPrefix` 为空** —— 若被设成 `Testing-` 之类，插件会去读写测试文件夹
2. **设置页填邮箱 + 授权码**，点「测试连接」
3. **不需要安装 7-Zip 或任何外部归档工具** —— 归档由内置纯 JS 实现

`private: true` 只挡 `npm publish`，不影响 git 安装。

## 验证清单（前 8 条）

1. 一台上传 500 MB 目录 → 网页版邮箱能看到该文件夹里有若干封带 `[SYNC-SHUTTLE]` 主题的邮件
2. 另一台刷新 → 项目卡片显示「远端完整」+ 正确片数
3. 下载并镜像 → 目标目录内容与源目录**逐文件 SHA-256 一致**
4. 删掉远端第 3 片 → 项目显示「缺第 3 卷」，下载被拒绝
5. 手动改坏某片一个字节 → 报「第 N 卷哈希不符」并重下
6. 上传过程中强杀 DSH → 5 分钟内另一台拿不到锁，超期后可抢
7. 删掉本机 `projects.json` → 刷新页面自动从远端备份恢复，原文件改名为 `.bak-<ts>`
8. 本机配置合法时打开清单 → **不发起任何远端请求**（快路径）

### 实现时必须守住的几条

这些是当前架构的硬性约束，违反会导致静默故障（测试能发现，但 `node --check` 发现不了）：

| 约束 | 违反的后果 |
|---|---|
| **ZIP 中央目录在文件末尾** | 多片时只读首片必报 `End of central directory not found`，读之前必须先拼回整包 |
| **`findVolumes` 的 baseName 必须是纯文件名** | 传完整路径进去，`readdir` 出来的名字做 `startsWith` 永远不匹配，「多片自动补齐」静默失效 |
| **必须自己校验 CRC32** | zip.js 的 `getData()` 不校验 CRC；数据区改坏一个字节它照样返回全量数据 |
| **`list()` 必须给出 `createdAtMs`（服务器时钟）** | 清单无法确定「哪个版本最新」，两台机器可能算出不同结果 |
| **`config` 的 `get()` 必须返回完整 meta** | 返回 `null` 会让配置备份的完整性校验悄悄失效 |
| **邮件头值必须纯 ASCII** | 中文被 RFC 2047 编码，mailparser 不解自定义头，永远匹配不上 |
| **读头必须 `toLowerCase()`** | 头名被服务器规范化大小写，区分大小写会全部读不到 |
| **`mailbox lock` 不可重入** | 持锁时再取锁会永久死锁 |
| **日志必须脱敏** | 授权码、完整邮箱地址会进日志文件 |

## 不做

- 不做自动定时同步（全手动，符合"两台不同时开机"的场景）
- 不做任意版本数 / 历史归档（只支持 1 或 2 版，不当网盘用）
- 不做锁的公平队列 / 优先级（家里两台电脑，串行就够）
- 不做加密（ZIP 无法隐藏文件名；需要保密请勿用本插件）
- 不做断点续传的跨会话续传语义（`tmp/fetch` 保留 7 天用于同一操作重试）
- 不做增量 / 块级同步（每次全量）
