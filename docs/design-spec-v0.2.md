## 2. 核心概念

### 2.1 项目（Project）

```
项目 Project
 ├─ name        「照片归档」           ← 跨机唯一标识，键值
 ├─ versions    [v1, v2, v3]          ← 只保留最新 1 个
 └─ binding     本机绑定的绝对目录      ← 只存本机，绝不上传
      PC-A → D:\work\照片归档
      PC-B → E:\shared\照片
```

**四条铁律：**

1. **项目名全局唯一，不允许创建同名项目。** 名字是跨机识别键，**唯一性判定用解码后的原文严格相等**——不做大小写归一、不做空白裁剪、不做 Unicode 归一化（NFKC 等），因为归一化会让 `Ａ`(全角) 和 `A` 变成同一个名字，反而制造歧义。
   - 进邮件头时用 `encodeURIComponent` 编码（§3.2 铁律），**读出来先 `decodeURIComponent` 再比较**
   - 输入里如果含首尾空格，**保存前显式提示**「名称首尾有空格，是否保留？」而不是静默裁剪
   - 如果输入的名字在**本地已绑定**或**远端已存在**，一律拒绝创建。
2. **本地目录绑定只在本机生效。** 两台电脑的路径本来就可能不同（`D:\work\照片归档` vs `E:\shared\照片`），所以**绝不跨机合并**。
   **但会以「本机专属备份」形式上到远端**，仅用于**这台机器自己**配置丢失后的恢复（见 §3.5）。备份是单向存档，不是共享状态。
3. **绑定目录可在清单中随时修改。** 选中项目 → 「更改本地目录」，指向新路径即可。改绑定不影响远端数据，也不删除原目录内容（原目录原样保留，只是不再被这个项目使用）。
4. **一台机器的同一个目录只能绑定一个项目**，防止同一目录被两个项目重复上传与互相覆盖。

### 2.1.1 项目从哪来：发现 vs 创建

项目清单 = **远端发现的项目 ∪ 本地已绑定的项目**。

| 来源 | 含义 | 本机可做的操作 |
|---|---|---|
| 远端有、本地也绑定 | 完整可用，两端都在 | 上传 / 下载 / 改绑定 / 删除 |
| 远端有、本地未绑定 | 另一台电脑传的，本机还没认领 | **绑定本地目录**（不能"创建"） |
| 本地已绑定、远端还没有 | 本机新建但从未上传 | 上传 / 改绑定 / 删除 |
| 都没有 | 全新项目 | 「新建项目」 |

**所以「新建」只用于四个都没有的全新名字**；想在第二台电脑上用别人传过的项目，是「在清单里选中它 → 绑定本地目录」，而不是新建。这样同名冲突从设计上就不可能出现。

创建时若名字撞车，报错文案：「项目『照片归档』已存在（远端 / 本地），请在清单中选择它并绑定目录」，并直接高亮定位到那个项目。

### 2.2 版本（Version）

每次上传 = 目录当前状态的一个快照 = 一个新版本。

- 版本号 = 时间戳 `20261119T152041`（UTC），显示时转本地时间并编号「v3」
- **版本保留数由每个项目独立决定**（默认 1 = 只留最新，见 §2.3）
- 删除前必须确认新版本**已完整写入并回读校验通过**，否则不删旧的（否则一次失败会把唯一的副本弄丢）

### 2.3 每项目版本保留策略

**全局默认「只留最新」（保留 1 份），单个项目可开启「保留上一版」（保留 2 份）。**

| 保留数 | 名称 | 邮箱占用 | 能回滚 |
|---|---|---|---|
| **1**（全局默认） | 只留最新 | 1× | ❌ |
| **2** | 保留上一版 | 2× | ✅ 回到上一版 |

**开关放在哪：项目卡片的 `⋯` 菜单 → 「保留上一版」勾选项。** 设置页有全局默认值，新建项目继承它。

**这个开关存在哪里：写在该项目最新版本的邮件头 `X-Sync-Shuttle-Keep-Prev` 里。**

理由与 §3.4 一致——**影响远端数据的配置，必须跟数据一起存**。如果只存本地，PC-A 开了、PC-B 看不到，两台机器对上传承删行为的预期就分裂了。

后果要说清楚：**开关的生效时机是「下一次上传」**。因为改开关不该立刻删数据，也不该立刻补数据（补不回来）。所以：

```
PC-A 勾选「保留上一版」→ 本地立即记录意图 → PC-A 下次上传时
  → 新版本写入时带 X-Sync-Shuttle-Keep-Prev: 1
  → 校验通过后，只删「第 3 个及更早」的版本，保留最新 2 个
```

**PC-B 打开清单时读最新版本头里的这个值**，所以 PC-A 上传一次之后，PC-B 就能看到开关已开。PC-B 自己改开关，同样在 PC-B 的下次上传才生效——**没有实时双向同步，也没有冲突**，因为最终以「最近一次上传者写入的值」为准。

**从「保留 2」改回「保留 1」的行为**：下一次上传校验通过后，保留数降到 1，多出来的历史版本一并删除。UI 上提示「下次上传后将删除 N 个历史版本」。

## 3. 邮件即传输层，信封即清单

数据全部存放在 QQ 邮箱文件夹 `Sync-Shuttle` 里，**不走 SMTP、不进收件箱、不触发通知、只存一份**（方案 B）。

### 3.1 主题格式

```
[SYNC-SHUTTLE] 照片归档 | v3 | 卷 2/12
```

**主题只负责"给人看"，不承担机器解析** —— 项目名里可能含 `|`、`/`、换行，用它当解析依据一定有 bug。所有机器判定一律走 §3.2 的自定义头。

项目名进主题前做**显示净化**：把 `|` 替换为 `｜`（全角）、换行与制表符替换为空格、截断到 60 字符。这只是显示层面，不影响头里的真实名字。

### 3.2 自定义头

> ⚠️ **铁律：所有自定义头的值必须是纯 ASCII。**
> 实测：nodemailer 会把含中文的头值编码成 RFC 2047（`=?UTF-8?B?...?=`），而 **mailparser 不会解码自定义头**（返回原始编码串）。中文一旦进头，就永远匹配不上。
> 所以：**头里只放机器标识，人读的中文放主题和正文。**

| 头 | 值 | 示例 | 用途 |
|---|---|---|---|
| `X-Sync-Shuttle-Project` | 项目名的 **percent-encoding**（`encodeURIComponent`） | `%E7%85%A7%E7%89%87%E5%BD%92%E6%A1%A3` | 归组（机器判定键）；读回用 `decodeURIComponent` |
| `X-Sync-Shuttle-Version` | 版本时间戳（UTC，ASCII） | `20261119T152041` | 版本标识，可排序 |
| `X-Sync-Shuttle-Version-Id` | 随机短 ID（ASCII） | `SS-7K2M9Q` | 见下方说明 |
| `X-Sync-Shuttle-Volume` | `序号/总数` | `2/12` | 卷序号 |
| `X-Sync-Shuttle-Volume-Bytes` | 本卷字节数（十进制） | `41943040` | **服务器 SIZE 不可信，必须自带** |
| `X-Sync-Shuttle-Volume-Sha256` | 本卷 SHA-256（小写 hex） | `3f2a…` | 逐卷校验基准 |
| `X-Sync-Shuttle-Archive-Bytes` | 归档总字节数（未分卷时的大小） | `1135126488` | 校验 B：卷数与字节和 |
| `X-Sync-Shuttle-Archive-Sha256` | 整个 .7z 的 SHA-256 | `8b1c…` | **校验 E：合并后整包比对（此前遗漏）** |
| `X-Sync-Shuttle-Source-Bytes` | 解压后（压缩前）总字节 | `1181116006` | 显示与校验 F |
| `X-Sync-Shuttle-Source-Files` | 源文件个数 | `842` | 校验 F |
| `X-Sync-Shuttle-Encrypted` | `1` / `0` | `0` | 决定是否需要弹口令 |
| `X-Sync-Shuttle-Keep-Prev` | `1` / `0` | `0` | 本项目版本保留策略（**随数据存，跨机可见**） |

**为什么需要两个版本标识（Version 与 Version-Id）：**

| 字段 | 作用 | 为什么不能只有一个 |
|---|---|---|
| `Version`（时间戳） | **排序与显示**，决定谁是"最新"、谁是"上一版" | 改系统时钟会重复；同一秒内两次上传会撞 |
| `Version-Id`（随机） | **唯一键**，用于定位"这个版本的那批邮件"、临时文件名、重试时定位半成品 | 纯随机无法排序 |

两者组合 = **可排序且不撞车**。清单归属判定用 `Project + Version`，删除/重试定位用 `Version-Id`。

### 3.3 正文清单

**每封邮件的正文都携带该版本的完整清单**（冗余设计，任一封都能重建全貌）：

```
project=照片归档
version=20261119T152041
versionId=SS-7K2M9Q
volumes=12
compression=7z -mx1
encrypted=false
topDir=照片归档
sourceFiles=842
sourceBytes=1181116006
archiveBytes=1135126488
archiveSha256=8b1c9d2e...
created=2026-11-19T15:20:41Z
volumeList:
  1|41943040|3f2a8c1d...
  2|41943040|8b1c9d2e...
  ...
  12|1342177|a71b3f90...
```

**格式定义（实现必须严格按此解析，不要用自由文本）：**

| 项 | 规则 |
|---|---|
| 头部字段 | 每行 `key=value`，`=` 后原样取值（不 trim） |
| 分隔符 | **`|`（竖线）**，**恰好 3 段**：`卷号|字节数|SHA-256` |
| 卷号 | 从 **1** 开始，连续递增，无占位 |
| 行数 | **与 `volumes` 严格相等**，不做任何截断 |
| 顺序 | 按卷号升序 |
| 编码 | UTF-8；行尾 `\n`（不用 `\r\n`） |
| 未知字段 | 忽略（向前兼容） |
| 缺失字段 | 视为清单不可用 → 该封降级为"仅凭头判断"，并在 UI 标注 |

**为什么不做截断**：一段清单 12 卷约 12×80 = 960 字节，500 卷也才 40 KB，对邮件正文毫无压力。截断只会制造"最后几卷无从核对"的破窗。

**解析失败怎么办**：正文清单是**冗余副本**，不是唯一来源。若正文解析失败，仍可用该封的**自定义头**（`Volume` / `Volume-Bytes` / `Volume-Sha256` / `Archive-*`）判断单卷，只是失去"全局视野"。此时 UI 标注「该版本清单不完整，请以邮件头为准」，**不阻断下载**（每卷的头信息足以完成校验 D）。

### 3.4 清单存在哪里（三种数据，三种去向）

这是最容易搞混的一点。系统里有**三份不同性质的数据**，绝不能混存：

| 数据 | 存在哪 | 是否权威 | 丢了会怎样 |
|---|---|---|---|
| **远端项目清单**<br>（项目名、版本、卷数、每卷字节与 SHA-256、总大小） | **邮件本身**：`Sync-Shuttle` 文件夹里每封的主题 + 正文 + 自定义头 | ✅ **唯一事实来源**，多机共享 | 不会丢——它就在服务器上，任何一台装了本插件的电脑都能重新读出来 |
| **本机绑定表**<br>（项目名 → 本地目录） | ①本机 `{{DSH_HOME}}\sync-shuttle\projects.json`<br>②远端 `Sync-Shuttle-Config` 文件夹里的本机备份 | ✅ **本机权威**（远端那份只是备份，不参与合并） | 本机文件丢了 → 从远端备份自动/手动恢复 |
| **派生缓存**<br>（上一次扫描到的项目/卷列表，用于加速首屏） | 本机 `{{DSH_HOME}}\sync-shuttle\cache\manifest.json` | ❌ 可随时删除 | 无影响，下次刷新自动重建 |

**核心原则：数据本身（项目内容 + 版本清单）以邮箱为唯一事实来源；本机配置（目录绑定）以本机为准，远端只做单机备份。**

理由：如果把**项目清单**也存一份到本地当权威，两台电脑各存一份，立刻就会出现「A 改了、B 不知道」的同步难题——这正是整套方案一开始要避免的东西。
而**目录绑定**恰恰相反：它是**纯本机信息**，两台机器的值本来就不同、也不该相同，所以不存在"谁对谁错"，只需要"别丢"。**备份**正好满足这个需求，且不会引入任何合并冲突。

**目录结构：**

```
{{DSH_HOME}}\sync-shuttle\
├─ projects.json          ← 绑定表（本机权威）
├─ machine.json           ← 本机身份（machineId，首次运行生成，永不变）
├─ cache\
│   └─ manifest.json      ← 派生缓存（可删）
├─ logs\
│   └─ sync-shuttle-YYYYMMDD.log
└─ tmp\                   ← 临时目录（build\ 与 fetch\ 清理策略不同，见 §10.4）
```

**日志规则：**

| 项 | 规则 |
|---|---|
| 文件名 | `sync-shuttle-YYYYMMDD.log`，按**本地日期**切分 |
| 保留 | **最近 14 天**，启动时删除更早的（一条 `Get-ChildItem` 过滤即可） |
| 单文件上限 | 50 MB，超过则当天不再写入并记一条"日志超过上限"到界面（防磁盘撑爆） |
| 内容 | 时间、级别、操作、项目名、卷号、字节、耗时、错误码 |
| **绝不记录** | 授权码、完整邮箱地址（脱敏为 `s********e@qq.com`）、加密包口令、邮件正文全文 |
| 级别 | 默认 INFO；设置页可切 DEBUG（会记每卷的时间与哈希，用于排查） |

远端另有一个独立文件夹：

```
Sync-Shuttle          ← 项目数据卷（所有机器共享读写）
Sync-Shuttle-Config   ← 各机器的配置备份（每台只读自己的）
  ├─ [SYNC-SHUTTLE-CONFIG] MC-7K2M9Q | DESKTOP-A | 2026-11-19T15:20:41Z
  └─ [SYNC-SHUTTLE-CONFIG] MC-3X8P2W | LAPTOP-B  | 2026-11-18T09:02:11Z
```


`projects.json` 结构：

```json
{
  "version": 1,
  "projects": [
    {
      "name": "照片归档",
      "localDir": "D:\\work\\照片归档",
      "createdAt": "2026-11-19T07:20:41.000Z",
      "updatedAt": "2026-11-19T07:20:41.000Z"
    }
  ]
}
```

**只有 `name` 和 `localDir` 是必需的**；卷数、大小、SHA-256 一律不落盘到这张表里——那些每次从邮件重新读，保证永远反映服务器真实状态。

**删除本机绑定 ≠ 删除远端数据。** `projects.json` 里删掉一条只是本机不再关联；远端邮件要删必须走「删除项目」并明确确认。两个动作在 UI 上分开，文案不同。

### 3.5 本机配置的远端备份（防配置丢失）

**问题**：插件升级、profile 重建、误删 `$DSH_HOME`、换机器迁移——任何一种都会让 `projects.json` 消失，而项目数据在远端好好的。只丢了一份 1 KB 的映射表却要手工重建几十个绑定，很冤。

**方案**：把绑定表以**「本机专属备份」**形式写到远端，仅用于这台机器自己恢复。

#### 存放位置

新建独立文件夹 **`Sync-Shuttle-Config`**，与数据文件夹 `Sync-Shuttle` **物理隔离**：

| 文件夹 | 内容 | 谁会读 |
|---|---|---|
| `Sync-Shuttle` | 项目数据卷（.7z.001…） | 所有机器，作为共享数据 |
| `Sync-Shuttle-Config` | 各机器的配置备份 | **只有对应那台机器自己** |

隔离的原因：数据文件夹的扫描逻辑要聚合「项目→卷」，混进配置邮件会污染清单；反之配置备份也不该被「删除项目」误删。

#### 机器身份

每台机器首次运行时生成一个稳定 ID，存在 `{{DSH_HOME}}\sync-shuttle\machine.json`：

```json
{ "machineId": "MC-7K2M9Q", "hostname": "DESKTOP-A", "createdAt": "..." }
```

- `machineId` 随机 6 位，生成后**永不变**（除非用户手动重置）
- `hostname` 只用于界面识别（「这是 DESKTOP-A 的备份」），**不作为主键**——主机名会变、会重名
- 备份邮件的主题：`[SYNC-SHUTTLE-CONFIG] MC-7K2M9Q | DESKTOP-A | 2026-11-19T15:20:41Z`

#### 什么时候写备份

| 触发 | 说明 |
|---|---|
| 新建项目并绑定目录 | 本地写成功后**自动**备份，异步，不阻塞界面 |
| **更改本地目录** | 同上 |
| 删除本机绑定 | 同上 |
| 设置页「立即备份配置」 | 手动补一次（备份失败后重试用） |
| **不自动定时** | 没变化就不写，避免产生垃圾邮件 |

同一机器**只保留最新一份**配置备份（写入成功并回读校验通过后，删除该 machineId 的旧备份邮件）。极端情况下配置本身很小（< 10 KB），仍走 7z 压缩 + 单封 APPEND，无分卷。

#### 恢复流程（自动，不弹阻塞确认）

```
本机 projects.json
  ├─ 存在且合法  → 直接用，**完全不联网、不看远端备份**
  └─ 不存在/损坏 → 自动扫描 Sync-Shuttle-Config → 找本 machineId 的备份
                    ├─ 有 → 下载 → 校验 → 解包 → 覆盖本地（损坏文件改名 .bak）
                    │      界面显示横幅：「已从 11-19 15:20 的远端备份恢复配置（8 个项目）」
                    └─ 无 → 空配置启动，设置页列出其他机器备份供手动复制
```

恢复是**自动**的：既然备份的唯一目的就是防丢，那么丢了就该直接恢复，而不是再问一次「要不要恢复」——用户在那个时刻除了「要」没有第二个合理选择。恢复后横幅告知，用户随时可以改回。

#### 三条不可违反的规则

1. **所有目录读取都走同一个入口，不允许绕过。** 任何需要「本机目录」的地方——显示项目清单、上传打包前取源目录、下载时取目标目录、备份/恢复本身——都必须调 `ensureBindings()`（见 §3.6），不许直接 `readFile('projects.json')`。这样"必要时拉远端"才有唯一实现点。
2. **本机合法就在本机解决，只有本机缺失才走远端。** 远端备份**永不覆盖**已存在的合法本机配置，防的是"旧备份盖掉新配置"。
3. **绝不跨机器自动套用。** 别的机器的路径（`D:\work\x`）套到本机（可能根本没有 D 盘）只会制造混乱。别的 machineId 的备份只列出，复制必须人工二次确认。

#### 为什么不直接在配置里跨机同步

因为那是**双向合并**问题：A 把「照片归档」绑到 `D:\a`，B 绑到 `E:\b`，同一项目两个不同的值，谁是权威？无论选哪边，都会把另一台机器的正确配置改错。

**备份只解决"丢失"，不解决"分歧"** —— 而目录绑定根本不需要解决分歧，因为每台机器的答案本来就该不一样。

### 3.6 统一入口 `ensureBindings()`（唯一读写口）

**这是全插件唯一允许触碰目录配置的地方。** 所有业务代码只调它，不直接读文件。

```
ensureBindings()
  ↓
① 读本机 projects.json
  ├─ 存在且 JSON 合法、结构完整
  │    → 返回 bindings，**不联网**（快路径，绝大多数情况走这里）
  │
  └─ 不存在 / 解析失败 / 结构非法
       ↓
     ② 扫描远端 Sync-Shuttle-Config，找本机 machineId 的备份
       ├─ 找到
       │    → 下载 → 校验 SHA-256 → 解包 → 校验 JSON 结构
       │    → 把损坏的本地文件改名 projects.json.bak-<ts>
       │    → 写入本地 → **返回 bindings，并置一个恢复标记**
       │    → 界面显示非阻塞横幅：「已从 11-19 15:20 的远端备份恢复配置（8 个项目）」
       └─ 未找到（或无自己的备份）
            → 返回空 bindings + 首次运行态
            → 界面提示：「未找到本机配置备份」+ 列出其他机器备份供手动复制
```

**关键设计点：**

| 点 | 决定 | 理由 |
|---|---|---|
| 命中本地时**不联网** | 只读本地文件 | 显示项目清单是高频操作，不能每次都连 IMAP |
| 自动恢复**不弹阻塞确认** | 恢复后用横幅告知 | 你要的是"必要时自动拉取"，弹窗会让每次启动都卡一步；且恢复是幂等的、可再改 |
| 恢复后**保留 `.bak`** | 损坏文件改名不删 | 万一是插件解析 bug 而非文件真损坏，用户还有原始文件可寻 |
| 恢复**幂等** | 连续调用只恢复一次 | 避免并发/多次渲染触发重复下载 |
| 结果**进程内缓存** | 内存持有 bindings + mtime | 只有检测到文件 mtime 变化才重读；写操作主动失效缓存 |

**写入路径（所有变更都走它）：**

```
mutateBindings(fn)
  ↓
① 加文件锁（同一时刻只允许一个写者）
  ↓
② 读当前 bindings（走 ensureBindings，保证基线正确）
  ↓
③ 执行变更（新增 / 修改 / 删除一条）
  ↓
④ 原子写本地：写临时文件 → fsync → rename 覆盖 projects.json
  ↓
⑤ 失效内存缓存
  ↓
⑥ **自动备份到远端**（异步，不阻塞界面）
    成功 → 更新"上次备份时间"，界面显示 ✅
    失败 → **不回滚本地变更**，界面显示 ⚠️「配置已保存到本机，但远端备份失败，将在下次变更或手动备份时重试」
  ↓
⑦ 返回新 bindings
```

**为什么备份失败不回滚**：目录绑定是用户当场做的操作，本地已经生效；因为网络问题把它撤销掉，用户体验更糟（"我明明改了，怎么又变回去"）。正确做法是本地为准 + 备份失败可重试。

**变更触发自动备份的三种情形**（与 §3.5 一致）：
- 新建项目并绑定目录
- 更改本地目录
- 删除本机绑定

## 4. 上传流程

```
选中项目 → 点「上传」
  ↓
⓪ 抢远端锁（§10.8）
   CREATE Sync-Shuttle-Lock
   ├─ 成功 → 写入锁邮件 → 回读确认 nonce → 启动 60s 心跳
   └─ 被占用 → 显示「远端正被 DESKTOP-B 使用」→ 自动排队（3s×20 次）
  ↓
① 前置检查
   - 项目已绑定目录且目录存在、可读
   - 7z.exe 可用
   - 目录非空
  ↓
② 7z 打包（进临时目录）
   7z a -t7z -mx1 -v40m <tmp>/<versionId>.7z <绑定目录>/.
   → 产生 .7z.001 … .7z.NNN
  ↓
③ 逐卷计算 SHA-256 + 字节数；向服务器查重（可选）
  ↓
④ 逐卷构造 RFC822 并发 APPEND
   nodemailer streamTransport → imapflow append()
   每卷之间间隔 600ms（避免服务器端过载）
   进度：第 k/N 卷、字节、瞬时速度、剩余时间、可取消
  ↓
⑤ 回读校验（关键，不可跳过）
   mailboxClose() → 重新 SELECT → 按主题定位本版本卷
   → 逐卷 fetchOne(seq,{source:true}) → mailparser 解附件
   → 比对 SHA-256 与字节数
  ↓
⑥ 全部通过 → 按项目的版本保留策略清理旧版本 → 清理临时目录
   保留 1（默认）：删除该项目的所有旧版本
   保留 2：删除第 3 个及更早的版本，保留最新 2 个
   任一失败 → 保留旧版本，报错并列出哪一卷失败、可重试该卷
  ↓
⑦ 释放远端锁（§10.8.4）
   确认锁邮件 nonce 仍是自己的 → 删锁邮件 → DELETE 锁文件夹
   （失败也不影响上传结果，只记日志；租期到期会自动失效）
```

**为什么第 ⑤ 步不能省**：这条链路已经验证可行，但「写入成功」不等于「读得回来」。上一轮实测就出现过写入成功、读回为空的情况（UID 问题）。没有回读校验，一次静默损坏就会在旧版本被删后变成永久丢失。

**清理旧版本（第 ⑥ 步）的具体规则：**

```
读出该项目所有完整版本（按 versionId 时间戳降序）
  keep = 新版邮件头 X-Sync-Shuttle-Keep-Prev === '1' ? 2 : 1
  待删 = versions.slice(keep)     ← 第 keep+1 个及之后
  → messageDelete(待删所有卷的 uid, {uid:true})
```

删除**只针对本项目**、**只针对完整版本**。不完整的残留版本（有卷但校验不全）不在正常清理范围内，需要用户在界面上显式「清理残留」。若删旧版本过程中断网，旧版本残留不会有危害——清单会显示多版本，可再删。**绝不允许「删旧版本的失败」影响新版本的有效性**，所以删除动作放在整个流程最后，且失败只记日志不报错给用户（除了提示"旧版本未清理"）。

## 5. 清单 / 项目列表

进入页面即扫描 `Sync-Shuttle` 文件夹（**每次刷新都 close + reopen**，因为 QQ 的 EXISTS 不刷新）。

```
┌─ 照片归档 ──────────────────────────────┐
│ 本机目录：D:\work\照片归档   [更改]   [⋯]│
│ 最新：v3  今天 15:20   1.18 GB / 12 卷   │
│ 状态：✅ 完整（12/12 卷，校验通过）       │
│ 版本保留：只留最新（1 份）                │
│ [上传新版本]  [下载并覆盖]  [删除项目]   │
└─────────────────────────────────────────┘
```

`⋯` 菜单里是低频操作：**保留上一版**（勾选）、清理残留版本、复制项目名。

**开了「保留上一版」的项目，卡片多一段历史版本：**

```
┌─ 照片归档 ──────────────────────────────┐
│ 本机目录：D:\work\照片归档   [更改]   [⋯]│
│ 最新：v3  今天 15:20   1.18 GB / 12 卷   │
│ 状态：✅ 完整（12/12 卷，校验通过）       │
│ 版本保留：保留上一版（2 份）  ▸ 占 2.28 GB│
│ ├ v2  11-12 09:03  1.10 GB / 11 卷 [下载]│
│ └ 下次上传后将删除 v2                     │
│ [上传新版本]  [下载并覆盖]  [删除项目]   │
└─────────────────────────────────────────┘
```

**项目卡片按来源分三种外观：**

| 外观 | 场景 | 主按钮 |
|---|---|---|
| 蓝色实心 | 远端有 + 本地已绑定 | 上传新版本 / 下载并覆盖 |
| 灰色虚线框 + 「待绑定」角标 | 远端有、本地未绑定 | **绑定本地目录** |
| 蓝色虚线框 + 「未上传」角标 | 本地有、远端没有 | 上传新版本 |

**「更改本地目录」的交互：** 点 [更改] → 选择新目录 → 提示

```
将「照片归档」的本地目录从
  D:\work\照片归档
改为
  E:\shared\照片

原目录内容不会被删除，只是不再与该项目关联。
```

确认后只更新本机绑定（走 `mutateBindings`），**自动触发远端配置备份**（异步），界面立即显示新路径。

**项目卡片上的目录一律来自 `ensureBindings()`**，不是任何本地缓存副本。因此本机配置丢失时第一次打开页面就会自动恢复并正确显示。

状态判定：

| 状态 | 条件 |
|---|---|
| ✅ 完整 | 卷数齐、每卷字节数对上、版本清单自洽 |
| ⚠️ 缺卷 | 缺失具体卷号，列出来 |
| ❌ 校验失败 | 读回后 SHA-256 不符，指出哪一卷 |
| ⬜ 仅本机有 / 仅远端有 | 一侧有项目记录、另一侧没有 |

**「哪一版算最新」的判定规则（唯一，不允许其他地方另立规则）：**

1. 按 `X-Sync-Shuttle-Version`（UTC 时间戳字符串）**降序排序**，取第 1 个为最新
2. 时间戳相同（同秒两次上传）→ 按 `Version-Id` 字典序升序取第 1 个，保证**结果确定、两台机器算出来一致**
3. 排序前先按 `Project`（解码后）+ `Version` 分组——同一项目同一版本的卷归为一组
4. **只有"完整"的版本参与"最新"的竞争**吗？——**不。** 最新就是最新，即使它缺卷。缺卷的最新版本要在卡片上**显著报错**（红色 ⚠️「当前版本缺第 3 卷，无法下载」），而不是悄悄回退到上一版（那会让用户以为自己下载的是最新的）。回退下载上一版必须由用户显式点历史版本行的 [下载]。
5. 排序结果**不缓存**（版本可能被另一台机器改动），每次刷新重算

**远端有、本机未绑定的项目（灰色「待绑定」卡片）：**

**照常显示版本信息**——最新版本、大小、卷数、状态、上传时间、来源机器，以及历史版本行。这些都来自邮件，与本机是否绑定无关。

只是这些按钮不可用或改变语义：

| 按钮 | 未绑定时 |
|---|---|
| 上传新版本 | **置灰**，tooltip「请先绑定本机目录」 |
| 下载并覆盖 | **置灰**，tooltip「下载需要目标目录，请先绑定」 |
| 查看版本详情 | **可用**（纯读取） |
| 绑定本地目录 | **主按钮**（高亮） |
| 删除项目 | 可用，但需二次确认（会删远端所有卷） |

- **不显示服务器报告的 SIZE**（是假的），体积一律取 `X-Sync-Shuttle-Volume-Bytes` 求和。
- 顶部显示容量条：`已用 X GB / 邮箱容量 Y GB`（Y 由用户在设置里手填，默认 16 GB）。

**容量统计与阈值（QUOTA 不可用，只能自己算）：**

| 项 | 规则 |
|---|---|
| **已用量怎么来** | `Σ 所有 Sync-Shuttle 邮件的 Volume-Bytes` + `Σ 所有 Sync-Shuttle-Config 邮件的实际字节数`（配置邮件无 Volume-Bytes 头，用解包后的 json 大小估算） |
| **为什么不精确** | 邮箱容量还含收件箱、已发送、其他文件夹、腾讯自身对齐损耗。本插件**只统计自己占的部分**，所以显示的已用量**必然小于**邮箱真实已用 |
| **所以要标注** | 容量条旁加 ⓘ：「仅统计本插件占用；邮箱真实用量请看网页版」 |
| **阈值分三档** | ≥ 80%：黄色提示「剩余 X GB」<br>≥ 90%：橙色 + 建议开启"只留最新"或删项目<br>≥ 100%：**红色并拒绝新的上传**（附链接到网页版检查） |
| **容量 Y 怎么设** | 设置页手填，默认 ~~16 GB~~ → **实际实现为 12 GiB**（见下方注）。旁边给一句提示「QQ 免费邮箱初始 2 GB，可手动免费翻倍 3 次到 16 GB；会员 2048 GB」 |
| **首次校验** | 设置页提供「测试容量」——发一封已知大小的测试邮件再删掉？**不做**（浪费且可能触发风控）。改为让用户自己填，并在首次上传后把实测的卷字节和与邮件实际占用差额记日志，供排查

> **实现注记（2026-11-20）**：容量基线最终定为 **12 GiB** 而非本文档写的 16 GB。
> 理由：QQ 免费邮箱上限 16 GB，但统计口径（Σ Volume-Bytes）**小于**真实占用，
> 且收件箱 / 已发送 / 对齐损耗都不在本插件统计范围内。贴着实测上限用，
> 等于把两处误差叠在一起，一旦占满会让**连正常收信都被服务商拒绝**。
> 留 4 GiB 余量的代价（少存几 GB）远小于风险。代码位置：`lib/paths.js` 的 `DEFAULTS.capacityBytes`。

## 6. 下载流程（镜像覆盖）

```
选中项目 → 点「下载并覆盖」
  ↓
⓪ 抢远端锁（§10.8）
   下载也要持锁：否则上传方的"清理旧版本"可能删掉你正在下的卷
   ├─ 成功 → 持锁到 ⑨ 结束
   └─ 被占用 → 「远端正被 DESKTOP-B 上传，预计 2 分钟」→ 自动排队
  ↓
① 校验远端完整性（卷全、字节数对）
  ↓
①.5 若 X-Sync-Shuttle-Encrypted=1 → **此刻就要口令**
     原因：步骤 ④ 的 `7z l -slt` 在 `-mhe=on` 时同样需要口令才能列目录
     （加密文件名时，连"里面有哪些文件"都读不到）
     → 弹口令输入框（密码框，不可见）
     → 立刻用 `7z l -slt -p<口令>` 验证口令正确性
     → 错则停在原地，**不下载一个字节**
     → 若用户取消 → 整个流程中止（不浪费下行流量）
  ↓
② 逐卷下载 → 临时目录，每卷立即校验 SHA-256
  ↓
③ 合并分卷 → 单个 .7z；整包 SHA-256 校验
  ↓
④ 用 `7z l -slt` 读出归档内完整文件清单（不落地）
   → 与目标目录现状比对，算出：
       将写入 / 覆盖：N 个文件
       将删除（本地独有）：M 个文件   ← 镜像语义
  ↓
⑤ 弹确认框（必须）：
   「将覆盖 N 个文件、删除 M 个文件，此操作不可撤销」
   [显示删除清单]  [□ 先备份被删文件到 <目录>\.ss-backup-<ts>]（默认不勾）
   → 用户确认才继续
  ↓
⑥ 7z x -aoa -o<目标目录> 解压覆盖
  ↓
⑦ 删除多余文件（步骤 ④ 算出的清单）
  ↓
⑧ 逐文件抽查校验 + 报告：路径、文件数、大小、耗时
  ↓
⑨ 释放远端锁
```

**安全设计（针对镜像语义的破坏性）：**

- 删除清单在**执行前**展示，不是事后告知
- 默认关闭备份，但提供勾选项（勾了就不删，改为移动到 `.ss-backup-<时间戳>/`）
- 目标目录必须**已存在且非盘符根目录**（拒绝 `C:\`、`D:\`，防手滑）
- 目标目录若与绑定目录相同 → 警告「正在覆盖自己的源目录」
- 整个流程可取消；取消时清理临时目录，已删除的文件无法恢复（这也是为什么提供备份选项）

## 7. 界面

左栏独立页面，形态对齐现有 IFOS 监控页（`ctx.slots` 注入 `sidebar.panellist` + `main`）。

四个分区：

## 9. 技术约束（全部实测确认，实现时必须遵守）

### 9.1 三个 QQ 坑

| 坑 | 现象 | 应对 |
|---|---|---|
| **UID 不可靠** | `fetchOne(uid, {uid:true, source:true})` 一律返回空 | 下载必须用 `fetchOne(String(seq), {source:true})`；seq 会漂移，**每次现列现读，不缓存** |
| **SIZE 是假的** | 13.5 MiB 的信报 887 字节 | 禁止用 SIZE 显示/预分配；`client.download()` 完全不可用（会抛 `DownloadOverflow`）；体积自带在邮件头里 |
| **EXISTS 不刷新** | append 后同一连接 fetch 仍是 0 封 | 每次刷新清单都要 `mailboxClose()` → 重新 `getMailboxLock()` |

### 9.2 其他

- `getMailboxLock()` **不可重入**：持锁时再取锁会永久死锁。每次取锁独立作用域，出作用域立刻 release。
- 单封上限 **51 MiB 附件**（raw 68.9 MiB），52 MiB 起报 `TOOBIG`。
- **QUOTA 不可用**（`getQuota()` 返回 false）→ 容量手填 + 自行统计（见 §5 容量规则）。
- 附件解码用 `mailparser.simpleParser`（已实测 SHA-256 一致）；**不要**手写 `indexOf` 解析（大字符串会爆栈）。
- 只在 `Sync-Shuttle` 文件夹内操作，**绝不触碰 INBOX / Sent**。
- 授权码不落盘明文、不进日志；界面与日志一律脱敏为 `s********e@qq.com`。
- **自定义头的值必须纯 ASCII**（中文会被 RFC 2047 编码且 mailparser 不解码，详 §3.2 与 §10.8.5）。项目名进头用 `encodeURIComponent`。
- **头名大小写不敏感**：写入 `X-Sync-Shuttle-Project` 会被规范化成 `X-Sync-Shuttle-Project`，读时必须 `toLowerCase()` 后比较。
- `mailboxDelete()` **对非空文件夹会失败**（`Command failed`），删文件夹前必须先清空里面的邮件，详见 §10.8.4。

### 9.3 依赖与环境

- 复用 profile 已有依赖：`imapflow 2.9.1`、`nodemailer 10.2.1`、`mailparser 3.12.4`（ESM import 走绝对 file URL）
- `C:\Program Files\7-Zip\7z.exe`（缺失时明确报错，不静默降级）
- 宿主 RPC：`ctx.webServer.register({kind:'prefix', path:'/sync-shuttle', handler})`，**不能用 `ctx.connection.rpc.handle()`**（实测 405）
- 单例兜底：`globalThis[Symbol.for('dsh-sync-shuttle.instance')]`，防热重载双实例
- 本机状态目录：`$DSH_HOME/sync-shuttle/`（沿用 ifos-monitor 等插件的既有约定，不在 profile 目录里塞数据）
- 启动时清空 `tmp\build\`（上次异常退出可能留下半截打包分卷）；**`tmp\fetch\` 保留**用于续传，规则见 §10.4
- 配置备份文件夹 `Sync-Shuttle-Config` 需同样先 `mailboxCreate()` 确保存在；写备份走与数据卷完全相同的 APPEND + seq 回读校验路径，只是单封、不分卷、体积 < 10 KB

## 10. 数据完整性保障

数据从「磁盘上的目录」到「另一台电脑的磁盘」要跨 **7 个可能损坏的环节**。核心思路只有一条：

> **每一次数据交接都算哈希，下一跳必须重算并比对；不一致就停在那里，绝不静默继续。**

### 10.1 完整性链条：7 个环节，6 次校验

```
  【本机】                        【网络/服务器】              【本机】

① 源目录 ──打包──▶ ② 归档 ──分卷──▶ ③ 分卷 ──APPEND──▶ ④ 邮箱存储
                     │                 │                    │
                  校验A              校验B               校验C
                  (7z t)          (逐卷 SHA-256)      (回读 SHA-256)
                                                           │
⑦ 目标目录 ◀──解包── ⑥ 归档 ◀──合并── ⑤ 下载的卷 ◀──下载────┘
    │                 │                │
  校验F             校验E            校验D
(文件数/字节)     (整包 SHA-256)   (逐卷 SHA-256)
```

**读图说明**：上半段是**上传**（从左到右，④ 是邮箱服务器），下半段是**下载**（从右到左，⑤ 是邮箱服务器）。④→⑤ 之间不是一次校验，而是**驻留期**——数据静静躺在服务器上，这期间没有任何人算哈希，风险是"用户手滑删信"和"容量满被清理"，对应表中「④→⑤ 存储」那一行。

| 环节 | 风险 | 校验手段 | 失败后果与处置 |
|---|---|---|---|
| **①→② 打包** | 源文件在打包过程中被改动；磁盘满；路径过长；符号链接/权限 | **校验A**：打包后立刻 `7z t` 全量测试，7z 内部 CRC32 逐数据块校验 | 立即失败，删临时目录，**不写任何邮件** |
| **②→③ 分卷** | 分卷大小异常、卷数不齐、最后一卷截断 | **校验B**：逐卷 SHA-256 + 字节数；卷数 = `ceil(归档大小 / 卷大小)` 必须吻合 | 同上，不写邮件 |
| **③→④ 上传** | APPEND 报成功但内容没落对；被服务器限流截断；`TOOBIG` | **校验C（最关键）**：`mailboxClose()` → 重新 SELECT → 按主题定位 → **用 seq 读回** → mailparser 解附件 → 重算 SHA-256 比对 | 该卷标记失败，可单独重试；**旧版本绝不删除** |
| **④→⑤ 存储** | 用户手滑删邮件、网页版误删、容量满被清理 | **清单自洽检查**：卷数/字节和与清单比对；缺卷就报错并指出缺第几卷 | 状态显示 ⚠️ 缺卷，下载被拒绝 |
| **⑤→⑥ 下载** | 读回内容损坏；seq 定位错邮件 | **校验D**：每卷下载后立刻 SHA-256 比对邮件头里声明的值 | 报「第 N 卷 SHA-256 不符」，中止合并 |
| **⑥ 合并** | 卷顺序错、缺卷、拼接错位 | **校验E**：合并后整包 SHA-256 与清单声明的整包值比对 | 中止，不触碰目标目录 |
| **⑥→⑦ 解包** | 7z 解压失败、镜像删除误删 | **校验F**：解压后比对文件数与总字节；7z 自身 CRC 再校一遍 | 已解压的部分保留，报告差异清单 |

### 10.2 三道「不可能静默损坏」的护栏

**护栏 1：新版本校验通过前，旧版本一封不删。**

这是最重要的一条。上传流程的删除动作**排在回读校验全部通过之后**：

```
写入新版本全部卷 → 回读校验全部通过 → 才删旧版本 → 才更新「当前版本」指针
                      ↓ 任一失败
                 保留旧版本，报错，可重试
```

后果：**远端任何时刻都至少有一个完整可用的版本**。哪怕新版本 11 卷都对了、第 12 卷失败，旧版本仍然完整。

**护栏 2：哈希值跟着数据走，不问服务器。**

QQ 的 `RFC822.SIZE` 是假的（13.5 MiB 报 887 字节），`download()` 因此完全不可用。所以体积与哈希**必须自带在邮件头 + 正文里**，成为清单的一部分。这不只是绕开 bug，更是把「校验基准」和「被校验数据」放在一起：即使服务器重编码了附件（实测没有，但不能假设），比对也会立刻发现。

**护栏 3：清单在每封邮件里都完整冗余一份。**

12 封邮件 = 12 份完整清单。删到只剩 1 封，仍然知道：这个项目应有几卷、每卷多大、每卷哈希多少、缺的是哪几卷。几百字节的冗余，换来「永远知道丢了什么」。

### 10.3 完整性检查的四个检查点（实现时的硬性要求）

| 检查点 | 时机 | 检查内容 | 不通过怎么办 |
|---|---|---|---|
| **CP1 打包自检** | `7z a` 完成后 | `7z t` 全量测试；卷数与预期吻合 | 拒绝上传 |
| **CP2 上传回读** | 全部 APPEND 完成后 | 逐卷 seq 读回 + 解附件 + SHA-256 | 标记失败卷，保留旧版本，可只重试失败卷 |
| **CP3 下载逐卷** | 每卷落临时文件后 | SHA-256 + 字节数 | 中止，指出哪一卷 |
| **CP4 解包后** | `7z x` 完成后 | 文件数、总字节、7z CRC | 报告差异，不静默通过 |

**CP2 的成本要说明白**：回读会把整包再下载一遍（40 MiB 报文约 10 秒，1 GB / 12 卷约 2 分钟）。这是**下行**流量（家宽下行远快于上行），且换来的是"敢删旧版本"的资格。因此**默认全量校验，不提供"跳过"开关**——一次静默损坏的代价是永久丢数据，不值得为 2 分钟冒险。

### 10.4 幂等与可重试

失败不能要求从头再来。

| 场景 | 设计 |
|---|---|
| 某卷 APPEND 失败 | 记录 `versionId + 卷号`，只重试该卷；重试前先删同 versionId 同卷号的半成品（防重复） |
| 某卷回读校验失败 | 删该卷重写；连续失败 3 次则整体中止并保留旧版本 |
| 下载中断 | 已下好的卷留在临时目录并带 `.ok` 标记；重试时跳过已校验通过的卷 |
| 解包中断 | `7z x` 从断点不可续，但整包已校验 → 重跑一次解包即可（覆盖模式幂等） |
| 进程崩溃 | 见下方 `tmp/` 清理规则 |

**`tmp/` 目录的生命周期（解决"清空"与"续传"的矛盾）：**

`tmp/` 下按用途分子目录，**清理策略不同**：

```
tmp\
├─ build\<versionId>\       ← 上传打包产物
│     清理：任务结束（成功/失败/取消）立即删；启动时**全部**清空
│     理由：一旦进程崩了，半截分卷没有任何复用价值（源目录还在，重打包即可）
│
└─ fetch\<versionId>\       ← 下载中间产物
      内含：xxx.7z.001 等卷文件 + 同名 .ok 标记文件（内容为该卷 SHA-256）
      清理：任务成功后删；**启动时保留**，最多保留 7 天
      理由：家宽下行有限，已下好的 1 GB 卷重下很浪费
```

**启动时的具体动作：**

| 目录 | 启动时行为 |
|---|---|
| `tmp\build\*` | **全部删除**（半截打包产物无价值） |
| `tmp\fetch\<versionId>\` | **保留**，但逐卷校验 `.ok` 里记录的 SHA-256 与实际文件比对，不符的删除该卷（不删整个目录） |
| `tmp\fetch\<versionId>\` 且 mtime > 7 天 | 删除整个目录（防垃圾堆积） |
| 配置里选中某项目、准备下载时 | 若存在对应 `fetch\<versionId>\` 且 `.ok` 齐全 → 提示「发现上次未完成的下载，可续传（已下 N/M 卷）」并给 [续传] / [重新开始] 两个选项 |

**所以「启动时清空 tmp/」这句话只对 `build\` 成立**，`fetch\` 是要续传的。§9.3 里那条同步修正。

**所有重试都基于「已经算过的哈希不会变」**，所以重试只需重做失败的那一步，不需要重新打包。

### 10.5 镜像删除的破坏性控制

镜像语义（删除包里没有的文件）是整个系统唯一**不可撤销**的操作。四道控制：

1. **执行前展示**：删除清单在确认框里逐条列出，不是事后告知
2. **可选中备份**：勾选后不删，改为移到 `<目标目录>\.ss-backup-<时间戳>\`，保留原相对路径
3. **目录白名单**：目标目录必须已存在、非盘符根目录（拒绝 `C:\`、`D:\`）、非用户主目录
4. **源=目标警告**：目标目录与绑定源目录相同时，明确警告

### 10.6 配置文件的完整性

目录绑定虽然小，但丢了就得手工重建几十条。

| 措施 | 做法 |
|---|---|
| 原子写 | 写临时文件 → fsync → `rename` 覆盖，避免断电产生半截 JSON |
| 合法性校验 | 解析后校验 `version` 字段、`projects` 是数组、每条有 `name` 与 `localDir` |
| 损坏保留 | 恢复或重建前，把损坏文件改名 `.bak-<时间戳>` 而非删除 |
| 远端备份 | 每次变更后异步备份；备份本身也走 APPEND + 回读校验 |
| **备份要持锁吗** | **要**——写 `Sync-Shuttle-Config` 也是"改远端状态"，与上传/下载同属写操作（§10.8.6）。<br>但**失败不阻断**：拿不到锁就跳过本次备份，标记为"待补备份"，下次变更或手动备份时重试；**绝不因为抢不到配置备份的锁而让用户的绑定操作失败** |
| 恢复幂等 | 同一次启动内多次调用 `ensureBindings()` 只触发一次恢复 |
| 不覆盖 | 本机文件合法时，远端备份永不写回 |

### 10.7 已知的完整性边界（诚实说明）

**这套设计保证的是「损坏能被发现」，不是「数据永不会丢」。** 仍有三类无法覆盖的情况：

| 情况 | 后果 | 缓解 |
|---|---|---|
| **只留最新版本**（全局默认）→ 新版本上传成功、旧版本已删，之后新版本在服务器上被误删/损坏 | 无备份可回 | **重要项目在 `⋯` 菜单勾选「保留上一版」**（见 §2.3），拿 2 倍容量换一版冗余 |
| 邮箱容量满后被清理，或用户在网页版手工删信 | 该版本作废 | 上传前按手填容量预检，不足则拒绝并提示；缺卷状态会立刻暴露 |
| 源目录在打包过程中被其他程序改动 | 包里是"混合时刻"快照 | `7z t` 能发现结构损坏但发现不了语义不一致；建议上传前避免大批量写入 |

**关于第一类**：已按你的决定实现为**全局默认「只留最新」，单项目可开「保留上一版」**（§2.3）。所以「无备份可回」不再是普遍情况——你觉得哪个项目重要，就给那个项目开。开销是该项目容量翻倍、可回滚一版。

### 10.8 远端锁（防止两机同时操作）

#### 10.8.1 为什么需要它，以及它能防住什么

前面的完整性链条有一个前提：**同一时刻只有一个操作者在改远端数据**。这个前提不成立时会出现三类真实损坏：

| 并发场景 | 后果 | 锁如何解决 |
|---|---|---|
| PC-A 上传 v4、PC-B 同时上传 v5 | 两边都按"删掉其他版本"清理 → **互相删掉对方刚写好的卷**，两个版本都残缺 | 后到者拿不到锁，排队等 |
| PC-A 上传中，PC-B 正在下载 | 下载方拿到 v3 的卷，清理时 v3 被删 → 合并到一半缺卷 | 读写互斥 |
| 两机几乎同时改本机目录绑定并备份配置 | 两份配置备份先后到达 → 后者覆盖前者（这本就是"只留最新"，可接受，但应串行化避免交错） | 配置写入也持锁 |

**关键设计前提**：这不是"防恶意"，是"防手快"。两台机器都是你自己在操作，冲突窗口是几十秒级的偶发重叠，不是持续对抗。

#### 10.8.2 锁存放在哪里

**一个专用文件夹当锁文件**：`Sync-Shuttle-Lock`

```
CREATE Sync-Shuttle-Lock
  ├─ created:true  → 抢锁成功（我是唯一赢家）
  └─ created:false → 已被占用（服务器返回 ALREADYEXISTS）
```

**为什么用「文件夹的创建」而不是「写一封锁邮件」**：

| 方案 | 原子性 | 判定 |
|---|---|---|
| **CREATE 文件夹** | ✅ **服务器原子判定**，实测 3 条连接并发 6 次 CREATE 同一名字，**恰好 1 个 created:true**，其余 5 个 created:false | 返回值直接可用 |
| 写锁邮件（APPEND） | ❌ 两个 APPEND 都会成功，两封都进去了 | 要靠"谁的时间戳更早"来仲裁，而时间戳是客户端时钟，两台机器时钟未必一致 |
| 读-判断-再写 | ❌ 典型的 TOCTOU 竞态 | 不可用 |

**实测证据**（`probe-lock2.mjs` 疑点 1）：3 条独立 IMAP 连接、每连接 2 次、共 6 次并发 CREATE，结果 `created:true` 恰好 1 个（赢家 C/r0），另外 5 个全 `created:false`。`create.js` 的判定依据是服务器返回的 `ALREADYEXISTS` 响应码（RFC 5530），**不是客户端预判**。

#### 10.8.3 锁的两个组成部分

只有文件夹不够——文件夹只能回答"有人占着"，回答不了"谁占着、占了多久、是不是已经死锁"。所以锁的信息写在**文件夹里的唯一一封邮件**上：

```
Sync-Shuttle-Lock/（1 封）
  X-Sync-Shuttle-Lock-Owner: DESKTOP-A      ← machineId，谁持有
  X-Sync-Shuttle-Lock-Nonce: 69b45cf6c266d91b ← 本次持锁的唯一标识
  X-Sync-Shuttle-Lock-At: 2026-11-19T08:00:00.000Z ← 取得时刻（客户端时钟）
  X-Sync-Shuttle-Lock-Ttl: 300000            ← 租期毫秒
  X-Sync-Shuttle-Lock-Op: upload 照片归档 v4 ← 干什么（纯给人看）
```

**为什么用租期（TTL）而不是"用完删掉"作为唯一机制**：进程崩溃、断网、强制杀 DSH 都会导致没走到释放代码。如果没有租期，锁就永久残留，两台机器全部卡死。租期让锁**在无人续期时自动失效**——这是防死锁的兜底。

**续期（心跳）**：持锁期间每 60 s 重写一次锁邮件的 `Lock-At`（删旧信 + 写新信，或原地更新）。任何一次心跳失败都是"可能已失去锁"的信号，操作必须**在当前卷完成后立刻停下来**重新确认，不能盲目跑完。

#### 10.8.4 抢锁与释放的完整流程

**抢锁 `acquireLock()`**：

```
1. CREATE Sync-Shuttle-Lock
   ├─ created:true  → 进入 2
   └─ created:false → 进入 3（被别人占着）
2. 写入锁邮件（Owner/Nonce/At/Ttl/Op）
   → 回读确认 nonce 确实在里面（不信 APPEND 的成功返回值，见下方陷阱）
   → 成功：拿到锁，启动 60 s 心跳，返回 lease
3. 读现有锁邮件
   ├─ At + Ttl < now  → 判定为「陈锁/僵死锁」→ 删掉锁文件夹 → 回到 1 重试
   ├─ Owner == 我自己的 machineId → 是我的残留锁（上次崩溃遗留）→ 删掉 → 回到 1
   └─ 否则 → 返回「被 DESKTOP-B 持有，正在 upload 照片归档，已持 42 秒」→ 排队重试
```

**必须回读确认的原因**：`probe-lock` 第一轮出现 `append` 抛出 `Do not know how to serialize a BigInt` 异常，但**报文实际写进去了**（重开回读能看到）。**"抛异常"不等于"没写成"，"返回成功"也不等于"写对了"** —— 唯一的判据是回读里的 nonce 对不对。这一点和 §10.2 的护栏逻辑完全一致。

**释放 `releaseLock(lease)`**：

```
1. 读锁邮件，确认 Nonce 还是我自己的 ← 不是我的就绝不删（可能已被别人抢走）
2. 删除锁邮件（清空文件夹）
3. DELETE Sync-Shuttle-Lock
```

**为什么第 1 步不能省**：如果我的租期已过、PC-B 已经清掉我的锁并抢到了，此时我再去 DELETE 文件夹，就会**删掉别人正在生效的锁** —— 那等于锁完全失效。只删自己 nonce 的锁，是这条协议唯一的安全根基。

**DELETE 前必须先清空**：实测 `mailboxDelete` 对**非空文件夹会失败**（`Error: Command failed`），必须先删掉里面的锁邮件再删文件夹（`probe-lock2` 疑点 2 已确认）。

#### 10.8.5 实现时的四个坑（全部实测踩过）

| 坑 | 现象 | 应对 |
|---|---|---|
| **头名被规范化大小写** | 写入 `X-SS-Lock-Owner`，服务器存成 `X-Ss-Lock-Owner`（nodemailer 规范化） | 用 `h.toLowerCase().includes()`，**不要**区分大小写比对 |
| **头值中文被 RFC 2047 编码** | `X-Sync-Shuttle-Project: 照片归档` 存成 `=?UTF-8?B?54Wn54mH5b2S5qGj?=`，**mailparser 不解自定义头** | 头值只放 **ASCII**。中文项目名走 `encodeURIComponent`（§3.2），读回 `decodeURIComponent`；人读的中文放主题和正文 |
| **EXISTS 不刷新** | APPEND 后同连接 `fetch` 仍返回 0 封 | 读锁状态前必须 `mailboxClose()` 再 `getMailboxLock()` |
| **DELETE 非空文件夹失败** | `mailboxDelete` 报 `Command failed` | 先删锁邮件，再删文件夹 |

#### 10.8.5.1 文件夹被人为删掉 / 三个文件夹都不存在时怎么办

用户在网页版手滑删掉 `Sync-Shuttle-Lock`、甚至把三个文件夹全删了，是必然会发生的。**任何操作都不得假设文件夹已存在**：

| 情况 | 表现 | 处理 |
|---|---|---|
| `Sync-Shuttle` 不存在 | 清单为空 | 首次上传前 `mailboxCreate()` 自动建；建失败则明确报错（不能静默当作没数据） |
| `Sync-Shuttle-Config` 不存在 | 配置备份失败 | 备份前自动建；建失败只提示"备份失败"，**不影响本地绑定生效** |
| `Sync-Shuttle-Lock` 不存在 | 正常情况就是不存在（锁是临时的） | `acquireLock()` 第一句就是 `CREATE`，本来就不需要它先存在 |
| **`Sync-Shuttle-Lock` 存在但里面 0 封邮件** | 典型的崩溃残留（CREATE 成功、写锁信前死了） | 读锁 → 发现无锁邮件 → 视为**陈锁**（无法判定持有者，只能按超时算）→ 若 `INTERNALDATE` 无值则直接清掉重建；为避免误抢活锁，**等一个心跳周期（60 s）后再清** |
| **锁文件夹存在多封邮件**（心跳实现为"删旧写新"时可能残留） | 多个 nonce | 以 **INTERNALDATE 最新**的那封为准，其余视为垃圾一并清掉 |

**自动重建原则**：`mailboxCreate()` 对已存在的文件夹返回 `created:false`，不抛异常，所以"每次都尝试建一遍"是幂等且安全的——**不需要先 `list()` 判断**。这条能省掉大量"文件夹不见了"的分支代码。

#### 10.8.6 锁的粒度与持有范围

**一个全局锁**（`Sync-Shuttle-Lock`），不做每项目一把锁。

理由：所有操作最终都落到**同一个邮箱的容量与同一批邮件**上，而且清理旧版本会碰其他版本；项目级锁无法防止「两个项目同时上传把容量吃满」。全局锁简单、绝不会死锁嵌套，代价是两台机器**完全串行**——而这对"家里两台电脑偶尔同步"的场景完全够用。

| 操作 | 是否需要锁 | 说明 |
|---|---|---|
| 上传 | ✅ 全程持锁 | 打包→APPEND→回读校验→清理旧版本 |
| 下载并覆盖 | ✅ 全程持锁 | 读卷→合并→解包→镜像删除 |
| 删除项目 | ✅ 持锁 | 删邮件 |
| 改本地目录绑定 + 配置备份 | ✅ 持锁 | 避免两机配置备份交错 |
| **仅浏览清单** | ❌ 不持锁 | 只读，用最新快照；拿不到锁也**绝不能阻断浏览** |

**浏览绝不持锁**是硬性要求：否则 PC-A 上传一个大包时，PC-B 连页面都打不开。清单显示可以略微陈旧，但必须能打开。

#### 10.8.7 拿不到锁时用户看到什么

```
┌─────────────────────────────────────────┐
│ ⏳ 远端正被另一台电脑使用                  │
│ DESKTOP-B · 上传「照片归档」v4 · 已持 42 秒│
│ 预计还需 1 分 30 秒                       │
│ [自动等待（推荐）]  [取消]                │
└─────────────────────────────────────────┘
```

- **默认自动排队**：每 3 s 重试，最多 20 次（约 60 s）。剩最后 3 次时变成「仍在等待，可以继续等或取消」。
- **绝不静默失败**，也**绝不自动抢陈锁**（除了明确的超租期情况）。
- 队列里显示对方的**项目名与操作**，让用户知道"不是卡死，是另一台在干活"。

#### 10.8.8 时钟不一致怎么办

`Lock-At` 用的是**持锁方的客户端时钟**，另一台机器用自己的时钟算 `At + Ttl < now`。两台机器时钟差 5 分钟就会误判。

**实测数据**：`probe-lock2` 里 INTERNALDATE 与客户端指定值的差为 509 ms / 916 ms（服务器按秒级截断）。

**应对（两层）**：
1. **INTERNALDATE 作为第三方时间基准**：锁邮件的 `INTERNALDATE` 由**服务器**记录（实测忠实，误差 < 1 s），读锁时优先用它而不是头里的 `Lock-At` 来判租期。头里的 `Lock-At` 只用于显示。
2. **宽限期**：判定陈锁时额外加 60 s 宽限（实际 `At + Ttl + 60s < now` 才抢），把时钟漂移和网络延迟都盖住。

Windows 默认开启 NTP 对时，通常偏差 < 1 s，宽限期足够。

#### 10.8.9 与完整性链条的关系

锁**不替代**任何校验，它是校验能成立的前提：

```
持锁 → 打包 → APPEND → 回读校验 → 清理旧版本 → 释放
       └────────── 这一段里没有第三方改动 ──────────┘
```

**即使有锁，回读校验（§10.3 CP2）仍然强制**：锁防的是"另一台机器"，防不了"服务器自己出问题"（§9.1 的 UID/EXISTS 坑就属于服务器行为）。两者是不同层次的防护，缺一不可。

#### 10.8.10 验收标准（锁专项，编号 L1–L7）

| # | 验收项 |
|---|---|
| **L1** | **并发上传**：PC-A、PC-B 同时点上传 → 一台进入操作、另一台显示「远端正被 DESKTOP-A 使用」并自动排队；先完成的正常结束，后开始的成功完成；**两个版本都没有残缺** |
| **L2** | **跨机可见锁**：PC-A 上传中，PC-B 刷新清单**仍能打开**（不持锁），但所有写操作按钮置灰并提示原因 |
| **L3** | **崩溃遗留锁**：PC-A 上传中途强杀 DSH → 5 分钟内 PC-B 尝试上传，提示「DESKTOP-A 持有的锁尚未过期」；**超过 5 分钟 + 60 s 宽限后**，PC-B 能自动清掉陈锁并成功上传 |
| **L4** | **不误删他人锁**：人为把 PC-A 的租期改到已过期，PC-B 抢到锁后，PC-A 尝试释放 → **PC-B 的锁不被删除** |
| **L5** | **心跳续期**：上传一个 2 GB 包（>5 分钟）→ 过程中不发生"锁被抢"，说明心跳生效 |
| **L6** | **释放后立即可抢**：PC-A 正常完成后，PC-B 立刻点上传不需要等租期 |
| **L7** | **锁邮件头完整**：回读锁邮件，`Owner/Nonce/At/Ttl/Op` 五个头全部存在且值正确（注意头名大小写不敏感） |

> 主验收表见 §12（编号 1–50）；本节 L1–L7 是锁的专项细化，**编号独立不冲突**。

## 12. 验收标准

1. PC-A 建项目「测试」，绑定 `D:\test\a`（含子目录 3 层、842 个文件）→ 上传
2. 网页版 mail.qq.com 能看到 `Sync-Shuttle` 文件夹里有 12 封带 `[SYNC-SHUTTLE]` 的邮件，且**收件箱、已发送都没有**
3. PC-B **无法**新建同名项目「测试」（应报错并提示去清单选择）；清单里看到「测试」是灰色「待绑定」卡片 → 绑定 `E:\test\b` → 刷新后状态显示 ✅ 完整 12/12 卷
4. PC-B 下载 → 覆盖确认框正确列出「覆盖 N 个 / 删除 M 个」
5. 解包完成后，`E:\test\b` 与 `D:\test\a` **逐文件 SHA-256 完全一致**（含删除多余文件）
6. PC-B 用「更改本地目录」把绑定从 `E:\test\b` 改到 `E:\test\c` → 原目录 `b` 内容仍完整存在，卡片显示新路径，且不产生任何网络请求
7. PC-A 上传第二版 → 成功后旧版本 12 封邮件被删，清单只剩 v2
8. 手动删掉第 3 卷 → 状态变 ⚠️ 缺卷 3，下载被拒绝并指出缺第 3 卷
9. 手动破坏某一卷字节 → 下载报「第 N 卷 SHA-256 不符」
10. 全程日志无授权码、无完整邮箱地址
11. `Sync-Shuttle` 文件夹内无残留自检邮件
12. **配置自动备份**：PC-A 新建 / 改绑定 / 删除各一次 → `Sync-Shuttle-Config` 里始终只有 1 封 `MC-<A的id>` 备份，内容为最新
13. **自动恢复**：删掉 PC-A 的 `projects.json` → 刷新页面（不重启）→ **无需任何点击**即自动恢复，卡片目录显示正确，横幅提示「已从 … 的远端备份恢复」，原文件已改名 `.bak`
14. **不跨机套用**：PC-B 只看到 PC-A 的备份时，**不会自动使用**；设置页列为「其他机器的配置备份」，点「复制为我的配置」需二次确认
15. **不覆盖**：PC-A 的 `projects.json` 合法存在时，即使远端备份是旧的，本机文件**不被覆盖**，且显示清单时**不发起任何 IMAP 请求**
16. **备份失败不回滚**：断网状态下改绑定 → 本地立即生效，界面提示「远端备份失败，将重试」，恢复网络后一次变更或点「立即备份」即补上
17. **CP1 打包自检**：故意让源目录含一个 4 GB 稀疏文件 + 一个 0 字节文件 → `7z t` 通过，卷数与 `ceil(大小/卷大小)` 吻合
18. **CP2 拒绝静默降级**：把 `tmp` 磁盘写满制造打包失败 → 断言**没有任何邮件被写入**，旧版本完好
19. **新版本失败不动旧版本**：上传一个 12 卷的包，在第 10 卷时断网 → 断言旧版本 12 封邮件仍在，清单仍显示旧版本为 ✅ 完整
20. **可重试**：接着第 19 条恢复网络 → 只重试第 10–12 卷，成功后才删旧版本；中途失败不产生重复卷（同 versionId 同卷号只有一封）
21. **逐卷下载校验**：下载中途把某一卷在临时目录里改一个字节 → 报「第 N 卷 SHA-256 不符」，中止且不触碰目标目录
22. **镜像删除可回滚**：勾选「先备份被删文件」→ 被删的 M 个文件出现在 `.ss-backup-<ts>/` 下且内容与源一致
23. **全局一致性**：最终 `E:\test\b` 与 `D:\test\a` 递归比对，**文件名集合、每文件字节数、每文件 SHA-256 三项全等**
24. **保留策略默认值**：新项目上传两版 → 第二版成功后，第一版邮件**全部被删**，清单只剩 v2
25. **单项目开启保留**：勾选「保留上一版」→ 再上传一版 → 邮箱里**同时存在最新 2 个版本**，卡片显示 v2 历史版本行与「下次上传后将删除 v2」
26. **跨机可见**：PC-A 开了保留并上传 → PC-B 刷新清单，**看到「保留上一版（2 份）」**（读自最新版本邮件头 `X-Sync-Shuttle-Keep-Prev`）
27. **改回只留最新**：取消勾选 → 再上传 → 多出的历史版本被删，清单只剩最新 1 个
28. **删旧失败不影响新版本**：在删旧版本时断网 → 新版本仍为 ✅ 完整可用，界面提示「旧版本未清理」，恢复网络后可手动清理
29. **旧版本可下载**：在有 2 个版本的项目上点 v2 的 [下载] → 成功解包，内容与 v2 那次的源目录一致
30. **中文项目名端到端**：建项目名「照片归档-测试」→ 上传 → 用 IMAP 客户端直接读该封邮件的头，断言 `X-Sync-Shuttle-Project` 的值是 **percent-encoding 后的纯 ASCII**（不含 `=?UTF-8?B`），且 `decodeURIComponent` 后等于原文；PC-B 刷新能正确归组到同一项目
31. **项目名含特殊字符**：项目名带 `|`、`/`、空格、emoji → 上传成功；主题里的 `|` 被替换为 `｜`；头里仍是可解码的 ASCII；PC-B 归组正确、卡片显示原文
32. **同样名字不同全半角**：`Abc` 与 `Ａbc`（全角 A）→ **视为两个不同项目**，都允许创建（不做归一化）
33. **正文清单可解析**：读任一封邮件正文，`volumeList` 行数等于 `volumes`，每行恰好 3 段用 `|` 分隔，卷号从 1 连续递增
34. **正文清单损坏不阻断下载**：手工把某封邮件正文的 `volumeList` 改乱 → 该封降级为"仅凭头判断"，UI 标注「清单不完整」，但**下载仍能完成**且逐卷校验通过
35. **最新版本的判定确定性**：人为构造同一 `Version` 时间戳的两批邮件（不同 `Version-Id`）→ 两台机器刷新后**显示同一个"最新"**（按 Version-Id 字典序），不出现 A 说 v3、B 说 v3' 的分歧
36. **缺卷的最新版本不回退**：删掉最新版本的第 3 卷 → 卡片红色显示「当前版本缺第 3 卷，无法下载」，**不自动回退**到上一版；上一版仍可从历史行单独下载
37. **未绑定也能看版本信息**：在从未绑定过的 PC-B 上，灰色「待绑定」卡片**正确显示**最新版本、大小、卷数、状态、上传时间；上传/下载按钮置灰并给出 tooltip 原因
38. **加密包提前要口令**：上传时勾选加密 → PC-B 点下载 → **在下载第一个字节之前**就弹口令框；输错口令立即报错且**没有产生任何下载流量**；取消则整个流程中止
39. **容量阈值**：把设置页容量填成 0.1 GB 后上传 → 达到 100% 时**拒绝上传**并提示；填成合理值时三档颜色（80/90/100）都正确切换
40. **容量口径诚实**：容量条旁 ⓘ 提示「仅统计本插件占用」，且计算值 = 所有 `Volume-Bytes` 之和（与手工求和一致）
41. **续传不被启动清空破坏**：下载到第 5/12 卷时强杀 DSH → 重启后 `tmp\fetch\<versionId>\` 里前 5 卷与 `.ok` **仍在**；再次点下载提示「可续传（已下 5/12 卷）」，选择续传后只下剩余 7 卷
42. **打包产物必须清空**：上传到第 5/12 卷时强杀 DSH → 重启后 `tmp\build\` 被**清空**，无半截分卷残留
43. **.ok 被篡改会重下**：手工把已下载的某卷内容改一个字节（不改 `.ok`）→ 重启后该卷的 `.ok` 与实际哈希不符 → **该卷被删除并重新下载**
44. **fetch 目录 7 天清理**：把某 `fetch\<versionId>\` 的 mtime 改成 8 天前 → 启动后被整个删除
45. **配置备份持锁但失败不阻断**：PC-A 上传大包持锁期间，PC-B 改本地目录绑定 → 绑定**立即生效**，提示「配置已保存，远端备份稍后重试」；PC-A 结束后 PC-B 一次变更或点[立即备份]即补上
46. **手动恢复必须展示差异**：本机 8 个项目、远端备份只有 6 个（差 2 个）→ 点[从备份恢复] → 确认框**列出将被删除的 2 个项目名**，确认后原配置已备份为 `.bak-<ts>`
47. **三个文件夹被删光可自愈**：在网页版删掉 `Sync-Shuttle`、`Sync-Shuttle-Config`、`Sync-Shuttle-Lock` 三个文件夹 → 上传操作自动重建全部所需文件夹并成功；配置备份也自动重建
48. **空锁文件夹（崩溃残留）**：手动 CREATE 一个空的 `Sync-Shuttle-Lock` → 另一台机器点上传时**不会立刻抢**，等 60 s 心跳周期后清掉并成功；期间提示「检测到疑似残留锁」
49. **锁文件夹多封邮件**：往锁文件夹里塞 2 封锁邮件（不同 INTERNALDATE）→ 以最新的为准，其余被识别为垃圾并清理

## 13. 明确不做

- 不做后台常驻/定时同步（全手动触发）
- 不做双向合并/冲突解决（镜像单向覆盖）
- 不做增量/块级同步（每次全量）
- 不做多账号、多文件夹、多用户
- 不碰 INBOX / Sent / 其他文件夹
- 不做加密密钥管理（密码由用户每次输入或自己存）
- **不做任意版本数/历史归档**（只支持 1 或 2；不当网盘用）
- **不做锁的公平队列/优先级**（抢锁靠重试，先重试成功的先做；两台机器不需要严格 FIFO）
