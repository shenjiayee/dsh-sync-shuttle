测试时间：2026-11-19
账号：QQ 邮箱（imap.qq.com:993）
目标文件夹：`Sync-Shuttle`
脚本：本目录 `probe-*.mjs`（一次性验证，不进插件代码）

---

## 一句话结论

**方案 B 完全可行，读写链路已端到端跑通并通过 SHA-256 校验。**
而且它比原计划的 SMTP 路线**宽松得多**：单封附件上限约 **51 MiB**（raw 报文 ≈ 69 MiB），不是 SMTP 的 50M（含 base64 膨胀后实际只有 ~35 MB 原始数据）。

---

## 端到端验证结果（probe-e2e.mjs）

模拟一个 100 MB 的包切成 3 卷（30 + 40 + 30 MiB）上传，再从服务器读回合并：

| 环节 | 结果 |
|---|---|
| 3 卷写入 | 全部成功，8.5–11.0 秒/卷 |
| 重新列出并识别 | 3/3 卷全部找到 |
| 逐卷读回 + SHA-256 | 3/3 卷 **全部一致** ✅ |
| 合并后整包 SHA-256 | **一致** ✅ |
| 50 MiB 单封边界 | 写入 + 读回 **一致** ✅ |

吞吐参考：raw 40.5 MiB 读回约 10.6 秒（≈3.8 MiB/s），54 MiB 约 14 秒。

## 三个必须记住的 QQ 坑（会直接决定插件怎么写）

### 坑 1：UID 不可靠，必须用 seq 读

`fetchOne(uid, {uid: true, source: true})` **一律返回 null / 空**，即使 uid 是 append 刚返回的、LIST 里也能看到。
改用 **seq**（`fetchOne(String(seq), { source: true })`，不带 `uid: true`）就能读到完整报文。

→ 后果：插件的下载路径必须是「列出 seq + uid + 主题 → 匹配目标 → 用 seq 读」。
→ 又因为 **seq 会随别人删信而漂移**，绝不能跨会话缓存 seq，必须每次现列现读。

### 坑 2：RFC822.SIZE 是假的

一封 13.5 MiB 的信，服务器报 `RFC822.SIZE = 887~1046` 字节（差了 16000 倍）。
`BODYSTRUCTURE` 里的 part size 是准的，`mailparser` 解析出的附件 size 也是准的。

→ 后果：① 不能靠 SIZE 显示体积或预分配缓冲；② `client.download()` 直接不可用——它按谎报的 size 算出 2KB 上限，必然抛 `DownloadOverflow`；③ 体积信息应随包走（写在主题/正文/自定义头里），而不是问服务器。

### 坑 3：EXISTS 不刷新

同一连接里 append 完立刻 `fetch('1:*')`，仍是**空**（返回 0 封）。
必须先 `mailboxClose()` 再 `getMailboxLock()` 重新 SELECT，才能看到刚写的信。

→ 后果：插件每次「刷新清单」都要走 close + reopen。

---

## 另一个操作陷阱

`imapflow` 的 `getMailboxLock()` **不可重入**。持锁期间再取锁会永久死锁（本轮踩过，进程挂住 12 分钟）。
→ 每次取锁都在独立作用域里，出来立刻 `release()`。

---

## 对插件设计的影响（相对需求说明书 v0.1 的修正）

1. **分卷大小**：从 30 MB 提到 **40 MiB**（留 11 MiB 余量），单封 raw ≈ 54 MiB，稳妥。上限 51 MiB 不建议贴着用。
2. **不再需要 base64 膨胀系数计算**：限制的是 raw 报文（≈69 MiB），40 MiB 附件 → raw 54 MiB，安全。
3. **容量看护**：QUOTA 不可用 → 改为用户在设置页手填邮箱总容量 + 插件统计自己存了多少，或读网页接口（第一版建议手填）。
4. **清单来源**：不能问服务器要 SIZE → 元数据（包名 / 卷号 / 总卷数 / 每卷字节数 / SHA-256）必须写在**邮件主题 + 正文 + 自定义头**三处冗余，读清单时从 envelope + headers 取。
5. **删除**：`messageDelete(uids, {uid: true})` 可用且可靠（按主题精确匹配删除已验证多次）。
6. **降级方案仍成立**：标准 7z 分卷，用户不装插件也能用 7-Zip 手动合并。
